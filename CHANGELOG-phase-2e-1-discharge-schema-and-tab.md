# Phase 2e-1 — Patient discharge schema + מטופלים משוחררים tab (foundation only)

Adds the backend schema and frontend plumbing for Phase 2e's patient-discharge audit trail. שחרר button and current discharge flow are untouched — this PR is foundation only. Phase 2e-2 rewires שחרר to actually use the new flow.

## Why

Patient discharge currently captures no outcome data — clicking שחרר sets `status='released'` and an exit date, that's it. Phase 2e mirrors Phase 2d's lead-closure model for patients: a dedicated audit sheet (`מטופלים משוחררים`), the same three-disposition keys (`not_relevant` / `completed` / `stopped_early`), and a restore path that returns the patient to the lead pipeline.

Splitting Phase 2e into two PRs keeps the blast radius small:
- **2e-1 (this PR):** schema + tab + restore. Zero user-facing behavior change for existing flows.
- **2e-2 (next):** showCloseLeadModal refactor + שחרר button rewire + the actual discharge action.

## Migration approach

None needed. `מטופלים משוחררים` is a fresh sheet auto-created by `getOrCreateSheet_` on first read. No backfill, no schema change to the existing Patients sheet.

## Changed

### `apps-script/Code.gs`

- New constant `DISCHARGED_PATIENTS_SHEET = 'מטופלים משוחררים'`.
- New constant `DISCHARGED_PATIENT_COLUMNS`. `id` is prepended (Patients has no `id` column today; the audit sheet needs one for `upsertRowById_` dedupe). Shape: `['id', ...PATIENT_COLUMNS, 'dischargedAt', 'disposition', 'discharge_note']`.
- New `dischargePatient_(patient)`: lock + upsert to `DISCHARGED_PATIENTS_SHEET`. **Does NOT delete from Patients** — that side stays on the existing client-driven `saveAll → replaceHousePatients_` whole-house-replace path. 2e-2 wires שחרר to call both.
- New `restorePatient_(patient)`: writes a new lead to `LEADS_SHEET` with `stage='new'`, carrying over `name` / `house` and a fresh `created`. Discharge record preserved as audit. Other LEAD_COLUMNS start blank.
- Router cases for `action === 'dischargePatient'` and `action === 'restorePatient'`.
- `getData_` extended to read `dischargedPatients` and include the array in the payload.

### `public/app.js`

- `state.dischargedPatients = []`.
- `SCREENS` extended with `'discharged-patients'`.
- `normalizeDischargedPatient(p)`: calls `normalizePatient(p)`, layers `dischargedAt` / `disposition` / `discharge_note` via `pickField` aliases (matches the irrelevant-leads pattern that prevents next-round-trip drops).
- `loadAll` populates `state.dischargedPatients` from `data.dischargedPatients`.
- `renderDischargedPatients()`: empty-state when none; otherwise rows showing name, house, entry date, discharged-at, disposition (translated via `DISPOSITION_LABELS`), and discharge note when non-empty. In edit mode each row gets a `שחזר מטופל` button.
- `restorePatient(p)`: confirm dialog via `showConfirm`, then optimistic UI (remove from `state.dischargedPatients`, unshift new lead) + `apiPost('restorePatient', ...)` with rollback on failure.
- `renderAll()` calls `renderDischargedPatients()`.

### `public/index.html`

- New top-tab `<button class="tab" data-screen="discharged-patients">מטופלים משוחררים</button>` between תפוסה and גבייה.
- New `<section id="screen-discharged-patients">` with header (count pill) + list container reusing `.irrelevant-list` styling.

### `public/style.css`

Untouched. The new section reuses `.irrelevant-list` / `.irrelevant-row` / `.count-pill` / `.billing-empty` classes already shipped by the retention tab.

## Not changed (intentional)

- **שחרר button on the תפוסה tab — untouched.** Still calls `releasePatient(p)` which sets `status='released'` + exit date via `saveAll`. No audit row is written yet; 2e-2 wires that.
- `showCloseLeadModal` — untouched. 2e-2 refactors it to be reusable for both leads and patients.
- Patients sheet schema — untouched. No `id` column added there. The client-side patient id remains session-local (regenerated by `normalizePatient` on each load); that's a known constraint already acknowledged by the existing code.

## Safety

- `dischargePatient_` has **zero callers in 2e-1**. The router accepts the action, the function is defined and locked, but nothing in the frontend posts it yet. Net effect on production: an unused endpoint and a sheet that may get auto-created on the next `getData`. Zero risk to live flows.
- `restorePatient_` will be reachable from the new tab — but only if discharged rows exist. The sheet is empty on first load, so the button is unreachable until 2e-2 produces rows.
- `getData_` returning `dischargedPatients: []` is additive — older client code (if cached) ignores unknown response keys.

## Known limitation (will resolve in 2e-2)

After successful restore, the discharged row vanishes from the UI optimistically but **reappears on the next page reload** — because the backend preserves the discharge record as audit. 2e-2 decides the final shape: a `restored` flag column on the discharged sheet, or delete-on-restore. Flagged in code (`restorePatient` comment).
