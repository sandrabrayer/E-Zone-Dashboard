## 1. מה כבר קיים (בסיס לבנייה)

### 1.1 טאבים בגיליון

| טאב | מה יש בו היום | עמודות מרכזיות |
|---|---|---|
| `Payments` | שורה אחת לכל מחזור חיוב של מטופל. ורד מסמנת «שולם», «שולם חלקית» או «לא שולם». | `id` (`pay::house::name::entry::due`), `patientId` (שלישייה), `dueDate`, `amount`, `status`, `amountPaid`, `balance`, `coverageStart/End`, `paymentUid` (קבוע), `patientUid`, `payerUid` (תמיד ריק), `chargedAt/By` (= «דווח כשולם», **לא** «אושר בבנק»), `sourceUpdatedAt/Version`, `link*` |
| `Credits` | ספר ההחזרים והזיכויים. | `creditType` (`days_unused` / `prepaid_return` / `other`), `calculatedAmount` (לא ניתן לשינוי), `amount`, `overrideReason`, `approvedBy`, `payoutDate` (נגזר בשרת: ה-15), `status` (`pending`/`paid`/`cancelled`), `paidDate`, `method`, `basis` (JSON), `creditUid` |
| `BillingOverrides` | סכום חודשי מותאם, לכל מטופל ולכל חודש. חל רק על שורות שלא שולמו. | `id` (`ovr::patientId::month`), `month`, `amount` |
| `PaymentsTombstones` | תיעוד מחיקות של תשלומים (מגיע רק מ-reconcile). | `paymentUid`, `reason`, `values` |
| `AuditLog` | יומן פעולות. | `payment_link_*`, `credit_*` |

### 1.2 לוגיקת גבייה ב-`app.js`

- **מחזור:** יום הכניסה בחודש. בחודש קצר נלקח היום האחרון בחודש. אין תאריך חיוב הבא שנשמר בגיליון.
- **חלון שהייה:** כניסה ≤ תאריך ≤ יציאה. מטופל שוחרר בלי תאריך יציאה נחשב כמי שעזב.
- **תאריך הקיטום:** `RECORDS_COMPLETE_FROM = '2026-07-01'`. מחזורים שלפניו מוצגים, אבל לא נספרים כחוב.
- **כיסוי:** `paymentCoverage()` מחזירה תקופה שנרשמה, ואם אין כזו, תקופה מוסקת: D עד D + חודש − יום.
- **מע״מ:** `VAT_RATE = 1.18`. כל הסכומים בגיליון כוללים מע״מ. התצוגה מחלקת ב-1.18 ומעגלת כל שורה ל-2 ספרות.
- **הכנסות חודשיות:** ארבעה סכומים: נגבה, צפוי, זיכויים ונטו. «נגבה» ו«צפוי» לעולם לא מחוברים לסכום אחד. זה **חוזה בין הדשבורד ל-Outpatient**.
- **כך מסמנים היום תשלום:** טאב גבייה ← הרשימה של היום ← בחירה של «שולם» ב-select. שתי הקשות, בלי אישור, בלי אמצעי תשלום, בלי תאריך תשלום ובלי אסמכתא.

### 1.3 בקרה קיימת בשרת

- **`reconciliationReportNow()`** (מ-PR #151): נקרא רק מהעורך, וקורא בלבד. הוא כותב Google Doc עם סעיפים A–K:

| סעיף | מה הוא מזהה |
|---|---|
| A | ליד ששילם או נקלט, בלי שורת מטופל |
| B | מטופלים פעילים כפולים |
| C | רשומת שחרור פתוחה למטופל שעדיין פעיל |
| D | שמות פגומים (U+FFFD) |
| E | תשלום שלא משויך לאף מטופל |
| F | שולם אבל לא נקלט |
| G | מטופל פעיל בלי אף תשלום |
| H | כיסוי מחזורים מול תשלומים, לכל מטופל |
| I | חשד לתשלום כפול, ותשלומים שכבר בוטלו |
| J | זיכויים בלי מטופל, או זיכויים שגדולים מסך התשלומים |
| K | תשלום אחרי השחרור, או סכום שחורג ביותר מ-5% מהתשלום החודשי |

  הפונקציה כבר מזהה `void`/`מבוטל`, מוכנה ל-PR #144.
- **`nightlyIntegrityJob`** (02:30): בודקת מטופלים שנעלמו ותשלומים יתומים, ושולחת מייל ל-`ALERT_EMAIL`.
- **`accountingPayments` / `accountingCredits`**: פיד לקריאה בלבד מאחורי `ACCOUNTING_SECRET`, אינקרמנטלי (`updatedSince` + `cursor`), עם tombstones.

### 1.4 מה **אין** היום

- אין משתמשים **אורטל** או **סנדרה**. `SESSION_USERS = ['ורד','שירן','יעל']` ב-`lib/users.js` וב-`app.js`.
- אין הרשאות לפי תפקיד. כל משתמש מחובר יכול לערוך הכול.
- אין העלאת קבצים או תמונות בשום מקום: לא `type="file"` ולא נתיב upload.
- אין `paymentDate` (תאריך שהכסף שולם בפועל), אין אמצעי תשלום, ואין אסמכתא.
- אין דף בנק, אין התאמה ואין סטטוס «אושר».
- אין התראות איחור בשרת. ההתראות קיימות רק בדפדפן.
- השרת (`server.js`) לא שולח סוד ל-Apps Script. כתובת ה-`/exec` פתוחה (`ANYONE_ANONYMOUS`), ו-`requestUser_` סומך על `params.user`.

ב-21/09 הוחלט על אפליקציה נפרדת שהדשבורד מזין. על בסיס ההחלטה הזו נבנה הפיד `accountingPayments` (22/09), עם העיקרון «הדשבורד לא מחזיק שום מצב חשבונאי». לא ראיתי ריפו של אפליקציה כזו מהסשן הזה, ואני לא יודע אם התחילו לבנות אותה.

| קריטריון | אפליקציה נפרדת | מודול בדשבורד |
|---|---|---|
| מקור אמת | שני גיליונות שצריך לסנכרן. «אושר בבנק» גר במקום אחר מהתשלום. | גיליון אחד. האישור יושב ליד התשלום. |
| המשוב לוורד | ורד לא רואה מה אורטל מצאה, אלא אם בונים כתיבה חזרה לדשבורד. | ורד רואה «לא נמצא בבנק» על השורה שלה, באותו מסך. |
| כללי מחזור, כיסוי ומע״מ | עוד עותק של הכללים (כבר יש שניים: `app.js` ו-`Code.gs`) או תלות מלאה בפיד. | אותן פונקציות, ואותן בדיקות השוואה. |
| זהות מטופל ומשלם | צריך crosswalk מ-`patientUid` למשלם בצד השני. | `payerUid` אפשר למלא במקום. |

| איחוד עם Outpatient | טבעי לאפליקציה שהיא «צרכן» של שני פידים. | אפשרי דרך פיד קריאה מ-Outpatient (סעיף 13), אבל זה מכניס כסף של Outpatient לגיליון של הדשבורד. |
| עלות ותחזוקה | ריפו, Railway, Apps Script, clasp CI ו-PIN נוספים. | טאב אחד ועוד כמה טאבים בגיליון. |
| מה כבר נבנה | הפיד `accountingPayments` נבנה בדיוק בשביל זה. | הפיד נשאר שימושי (רו״ח, ייצוא, Outpatient). שום דבר לא נזרק. |

### ההמלצה: מודול בדשבורד

1. **הפעולה של ורד חייבת לקרות בדשבורד בכל מקרה**: הדיווח, האסמכתא והקישור לשורת המחזור. הבקרה של אורטל היא הצד השני של אותה שורה. אם מפצלים אותן לשתי מערכות, נוצר בדיוק הפער שקיים היום בין הוואטסאפ לאפליקציה.
2. **רוב הפערים של היום (A–K) הם איכות נתונים בדשבורד**: כפילויות, תשלומים יתומים ושמות פגומים. אפשר לתקן אותם רק בדשבורד. בקרה שיושבת מחוץ לדשבורד יכולה רק לדווח עליהם.
3. **כל עותק נוסף של כללי הגבייה הוא סיכון**, וכבר ראינו את זה: `monthKey` הוגדר פעמיים, והחוזה מול Outpatient מחייב בדיקות זהות. אפליקציה שלישית שמחשבת «מה היה צריך לגבות» היא עותק שלישי.
4. **הפרדת הסמכויות נשמרת**, אבל רק בתנאי שעושים קודם את תיקון האבטחה (שלב 0).

**מה היה הופך את ההמלצה:**
- אם אורטל צריכה לעבוד **בלי שום גישה** לנתוני מטופלים. המודול יציג רק שם, בית וסכום, בלי שום שדה קליני, אבל זה עדיין גישה לשמות.
- אם Outpatient הוא חלק גדול מהגבייה, ואורטל רוצה מסך אחד לשתי האפליקציות. במקרה כזה אפשר להמשיך עם האפליקציה הנפרדת, בתנאי שהיא **כותבת חזרה** סטטוס אימות לדשבורד, בפעולה מוגנת בסוד נפרד.
- **צריך החלטה של סנדרה** (שאלה 1 בסעיף 15).

## 4. מחזור החיים של תשלום

```
   [מחזור צפוי]  ← נגזר: יום הכניסה + חלון שהייה + override
        │  ורד: «דיווח תשלום» (סכום, אמצעי, תאריך, אסמכתא)
        ▼
   [דווח]  Payments.status = paid/partial,   PaymentReports.verifyStatus = reported
        │  אורטל: התאמה לשורת בנק
        ├──► [אושר]       verifyStatus = confirmed   (bankLineUid, verifiedBy/At)
        ├──► [פער סכום]   verifyStatus = mismatch    (הפרש נרשם, חוזר לוורד)
        └──► [לא התקבל]   verifyStatus = not_received (אחרי N ימים; חוזר לוורד)
   [כפילות]  Payments.status = void  (PR #144: לא נמחק, מוחרג מכל סכום)
```

**עיקרון:** את `Payments.status` **לא משנים**. הוא ממשיך להיות «מה ורד דיווחה», ועליו נשען החוזה של «נגבה» מול Outpatient. מצב האימות הוא **ציר נפרד** בטאב חדש, כך שהחוזה החוצה-אפליקציות לא מתפצל. במסך הבקרה בלבד יופיע מספר חמישי, «אושר בבנק», שלא נכנס לחוזה ההכנסות.

## 5. מודל נתונים: טאבים חדשים ועמודות

כל הטאבים **append-only בכותרות**. עמודה חדשה נכנסת רק בסוף, כי `readSheet_` ממפה לפי מיקום. תאריכים, חודשים ומזהים מאוחסנים כטקסט (`'@'`). כל חותמת זמן נקבעת בשרת, לפי שעון ישראל עם offset (`israelTimestamp_`), והמשתמש נלקח רק מהעוגייה החתומה.

### 5.1 `PaymentReports` (חדש): דיווח של ורד, שורה לכל אירוע

למה טאב נפרד ולא עוד עמודות ב-`Payments`: מחזור אחד יכול לקבל כמה תשלומים (חלקי, צ׳ק ועוד העברה), וכל אחד מהם צריך אסמכתא ואימות משלו. שורת ה-`Payments` נשארת שורת המחזור, ו-`amountPaid` שלה הוא סכום הדיווחים שלא נדחו.

| עמודה | משמעות |
|---|---|
| `reportUid` | `rpt-<uuid>`. **נוצר בלקוח** ומשמש מפתח אידמפוטנטיות, כדי ששליחה חוזרת מהטלפון לא תיצור שני דיווחים. |
| `paymentUid` | השורה ב-`Payments` שהדיווח שייך אליה. |
| `patientUid`, `houseId` | לסינון ולתצוגה. |
| `amount` | כולל מע״מ, ₪. |
| `method` | `transfer` / `check` / `card` / `cash` / `other` |
| `paidOn` | התאריך שבו המשלם שילם בפועל. ברירת המחדל היום, וניתן לשינוי. |
| `payerName` | אופציונלי. שם המשלם כפי שיופיע בבנק, ומשמש להתאמה. |
| `receiptFileId` | מזהה קובץ ב-Drive (פרטי), או ריק. |
| `note` | עד 300 תווים. |
| `reportedAt` / `reportedBy` | נקבעים בשרת. |
| `verifyStatus` | `reported` / `confirmed` / `mismatch` / `not_received` / `rejected` |
| `bankLineUid` | ריק עד שיש התאמה. |
| `verifiedAt` / `verifiedBy` | נקבעים בשרת. **רק תפקיד `controller`**. |
| `verifyNote` | נימוק לפער או לדחייה. |
| `sourceUpdatedAt` / `sourceVersion` | אותו דפוס כמו ב-`Payments`, בשביל הפיד. |

### 5.2 `BankLines` (חדש): שורות מדף בנק

| עמודה | משמעות |
|---|---|
| `bankLineUid` | `bnk-<uuid>` |
| `lineHash` | hash של (חשבון, תאריך ערך, סכום, אסמכתא, יתרה). מונע ייבוא כפול של אותו דף. |
| `account` | חשבון בנק או סוג סליקה. |

## 6. «דיווח תשלום» של ורד: שלוש הקשות במובייל

**המטרה:** שזה יהיה מהיר יותר מוואטסאפ. בוואטסאפ ורד צריכה לפתוח צ׳אט, לצרף, לצלם, ולהקליד שם וסכום: לפחות שש פעולות ועוד הקלדה, ואחר כך מישהו צריך להזין הכול מחדש.

### 6.1 הזרימה

```
הקשה 1  כפתור צף «₪ דיווח תשלום» (בכל מסך) ← רשימת מטופלים מסודרת:
        «מגיע היום» ← «באיחור» ← «בשבוע הקרוב» ← כל השאר (חיפוש בראש)
        ↓ הקשה על המטופל
הקשה 2  «📷 צילום אסמכתא» ← פותח את המצלמה האחורית ישירות
        (input type=file accept="image/*" capture="environment")
        (הלחיצה על הצמצם במצלמה היא של מערכת ההפעלה)
הקשה 3  «שליחה» ← הודעת אישור «נשלח ✓ — ₪30,000 · העברה · עמית ב.»
```

כל השאר כבר ממולא, ואפשר לשנות בהקשה:
- **סכום:** הסכום הפתוח של המחזור הנוכחי (אחרי override), ובמקרה של איחור, יתרת החוב.
- **אמצעי:** האמצעי האחרון של אותו מטופל, ואם אין כזה, «העברה».
- **תאריך תשלום:** היום.
- **מחזור:** המחזור הפתוח הוותיק ביותר. אם יש יותר מאחד, מוצג בורר.
- **בלי אסמכתא:** כפתור «שליחה בלי צילום» זמין, אבל השורה מסומנת «חסרה אסמכתא», ואורטל רואה את זה.

### 6.2 התנהגות

- **עדכון אופטימי:** השורה בגבייה הופכת ל-«דווח» מיד. אם השמירה נכשלת, ההודעה ברורה, והדיווח נשאר בתור.
- **רשת חלשה או בלי רשת:** הדיווח והתמונה הדחוסה נשמרים ב-IndexedDB («תור יוצא»), ונשלחים כשהרשת חוזרת. `reportUid` שנוצר בלקוח מבטיח שהשרת לא ייצור כפילות (upsert לפי `reportUid`). ה-service worker ממשיך **לא** לשמור `/api/` במטמון.
- **דחיסה בלקוח:** canvas עד 1600px, JPEG באיכות 0.7, כ-300 עד 500KB. נשלח base64 ב-POST, ובשרת יש מגבלה של 2MB.
- **אחרי השליחה:** הדיווח מופיע אצל אורטל בתור «לאימות». אם אורטל מסמנת «פער» או «לא התקבל», ורד מקבלת תג אדום על המטופל, עם ההערה של אורטל.
- **מעבר מוואטסאפ:** שבועיים במקביל. ורד ממשיכה לשלוח בוואטסאפ, ואורטל בודקת שכל הודעה קיימת גם באפליקציה. אחרי זה הוואטסאפ מפסיק להיות ערוץ רשמי.
- **הנתיב הישן נשאר:** ה-select «שולם» בטבלת הגבייה ממשיך לעבוד. כל שינוי ל-`paid` דרכו יוצר אוטומטית `PaymentReport` בלי אסמכתא, עם `method=''`, כך שאף דיווח לא עוקף את הבקרה.

### 6.3 אחסון האסמכתא (אבטחה)

- התיקייה ב-Drive היא **פרטית** לחשבון הסקריפט (`RECEIPTS_FOLDER_ID` ב-Script Properties). הקבצים **לא משותפים**, ואין קישור ציבורי.
- שם הקובץ הוא `reportUid.jpg`, בלי שם מטופל.
- הצפייה עוברת רק דרך הפרוקסי: הפעולה `getReceipt` מחזירה bytes אחרי בדיקת תפקיד (ורד, אורטל או סנדרה).
- בשרת יש בדיקות: MIME מותר רק `image/jpeg`, `image/png` או `application/pdf`, ובדיקה של magic bytes ולא רק של הסיומת. גודל עד 2MB.
- **שמירה:** האסמכתאות נשמרות שבע שנים (חובת שמירת מסמכים). צריך אישור של רו״ח, שאלה 9.

## 7. הבקרה של אורטל

### 7.1 המסך: טאב «בקרת גבייה» (תפקיד `controller` בלבד)

### 7.2 ייבוא בנק

- אורטל מעלה CSV או XLSX מהבנק, והפענוח נעשה **בדפדפן** (SheetJS מ-cdnjs). לשרת נשלחות רק שורות זיכוי מנורמלות.
- הייבוא אידמפוטנטי לפי `lineHash`. אם אותו דף מועלה פעמיים, אף שורה לא נוספת.
- **מבנה הקובץ תלוי בבנק.** צריך דוגמה אמיתית לפני שבונים (שאלה 7).

### 7.3 הצעות התאמה

ההצעות נוצרות בשרת, אבל **שום דבר לא מאושר אוטומטית**.

| ציון | כלל |
|---|---|
| 50 | סכום זהה. |
| 20 | `valueDate` בין יומיים לפני `paidOn` לעשרה ימים אחריו. |
| 20 | `payerName` או שם המטופל מופיע ב-`description`, אחרי נרמול. |
| 10 | אותו אמצעי, לפי סוג החשבון. |

- הצעה מוצגת רק כשהציון 70 ומעלה.
- הצעה **ייחודית** (מועמד אחד) מקבלת כפתור «אשר הכול» קבוצתי. גם זו פעולה של אורטל, לא של המערכת.
- סליקת אשראי: זיכוי אחד מחברת הסליקה, נטו מעמלה, יכול לכסות כמה דיווחים. במקרה כזה ההתאמה ידנית, וההפרש נרשם כעמלה.

### 7.4 הפרדת סמכויות

| מי | מה מותר |
|---|---|

הכללים האלה נאכפים **בשרת** (`Code.gs`), לא רק בממשק.

## 11. אבטחה והרשאות (תנאי מקדים)

### 11.1 שלב 0: לסגור את `/exec` (חובה לפני כל השאר)

**הבעיה:** `appsscript.json` מוגדר `"access": "ANYONE_ANONYMOUS"`, ו-`server.js` לא שולח סוד. מי שיודע את כתובת ה-`/exec` יכול לקרוא ל-`savePayment` ישירות, עם `user: 'סנדרה'`. ברגע שהשרת מתחיל לאכוף תפקידים לפי `user`, זה **עוקף את האכיפה**.

**התיקון:**
- Script Property `PROXY_SECRET` ומשתנה Railway תואם.
- `server.js` מוסיף `proxySecret` לכל GET ו-POST.
- `handle_` דוחה כל פעולה **בלי** `proxySecret` תקין. זה לא חל על הפעולות שיש להן סוד ייעודי משלהן: `accountingPayments`, `admittedRoster`, `meetingReport` וכדומה.
- ההשוואה בזמן קבוע.
- **אותו backend משרת גם את Managers ואת Therapists** (`APPS_SCRIPT_URL` / `DASHBOARD_SHEETS_URL`). צריך למפות אילו פעולות הם קוראים ולתת להם את הסוד, או להפריד deployment לקריאה בלבד. אחרת הם יישברו. **צריך תיאום.**

### 11.2 תפקידים

```
USER_ROLES = { 'ורד': ['reporter'], 'שירן': ['reporter'], 'יעל': ['reporter'],
               'אורטל': ['controller'], 'סנדרה': ['reporter','controller','approver'] }
```

- המפה מוגדרת **בשרת** (`lib/users.js` ו-Script Property), והלקוח רק מסתיר כפתורים.
- כל פעולת כתיבה חדשה בודקת תפקיד ב-`Code.gs` מול `requestUser_`, שאחרי שלב 0 אפשר לסמוך עליו.
- PIN: ה-PIN המשותף נשאר לשלב הזה. **מומלץ** PIN אישי לאורטל ולסנדרה, כי הן מאשרות כסף (שאלה 8).

### 11.3 עוד כללים

- הודעות שגיאה בלי פרטי מטופל.
- `AuditLog` לכל אימות, ביטול אימות, דחייה, חריגת החזר וסגירת פריט פתיחה.
- `/api/debug/last-save` שומר את גוף הבקשה האחרונה. **אסור** שיכיל base64 של אסמכתא. צריך לקטום את השדה ב-`summarizeBody`.

## 13. Outpatient: מה נדרש מהריפו `ezone-outpatient`

**לא ראיתי את הריפו מהסשן הזה.** כל מה שכתוב כאן הוא **בקשה**, לא תיאור. מה שידוע מ-`EZONE-ECOSYSTEM-STATUS.md`:
- יש עמודת `paymentDate` אמיתית, `nextBillingDate` לכל לקוח, וחיובים חד-פעמיים.
- `CLIENTS_HEADERS` הוא append-only.
- פירוט לפי `location`.
- יש חוזה הכנסות משותף עם הדשבורד.

### 13.1 שאלות שצריך לענות עליהן מתוך הריפו (לא לנחש)

1. מי מדווח שם תשלום, ואיך (ממשק, וואטסאפ, אחר)?
2. איזה מזהה יציב יש לכל לקוח ולכל תשלום? האם יש uid שלא משתנה כשמשנים שם או תאריך?
3. האם הסכומים כוללים מע״מ? החוזה אומר שכן. לאמת בקוד.
4. איך נרשמים זיכויים והחזרים, ומה המדיניות שם?
5. האם `createLead` (המעבר מהדשבורד, `released_outpatient`) **מחזיר מזהה לקוח**? הדשבורד שולח היום רק `{name, phone, house, note}` ולא שומר מה חזר. בלי מזהה כזה אין crosswalk בין מטופל שעבר לבין הלקוח שנוצר.
6. האם יש tombstones למחיקות?

### 13.2 נקודת הקצה המבוקשת: קריאה בלבד, אותה צורה כמו `accountingPayments`

`doGet?action=accountingPayments&secret=…&updatedSince=…&cursor=…&limit≤500`
- הגישה מאחורי Script Property **חדש** (`ACCOUNTING_SECRET` ב-Outpatient), fail-closed.
- אסור שתהיה דרכו גישה לפעולת כתיבה.

| שדה | הערה |
|---|---|
| `paymentUid` | קבוע, נוצר פעם אחת. |
| `clientUid` | קבוע. |
| `location` | סניף, להתאמה ל-`houseId` לפי אתר. |
| `amount`, `vatInclusive: true`, `currency: 'ILS'` | |
| `paymentDate` | התאריך שבו שולם בפועל. |
| `coverageStart` / `coverageEnd` או `nextBillingDate` | להקצאה לחודשים. |
| `status` | הערכים הקיימים שם, עם מילון. |
| `kind` | `cycle` / `extra_charge`. |
| `reportedAt` / `reportedBy` | אם קיימים. אם לא, ריק. לא לגזור. |
| `sourceUpdatedAt` / `sourceVersion` | |
| `historical` | כמו בדשבורד. |
| `fromDashboardPatientUid` | אם 13.1 סעיף 5 נפתר. |

ובנוסף:
- `accountingCredits`, באותה צורה, עם `creditUid`, `clientUid`, `amount`, `status` ו-`payoutDate`.
- `tombstones`.
- **בלי מידע קליני:** רשימת שדות מותרים (allow-list) בלבד, כמו בדשבורד.

### 13.3 מה הדשבורד יעשה עם זה

- משימת שרת יומית קוראת את הפיד ל-`ExternalPayments` (קריאה בלבד, שורות `source='outpatient'`).
- אורטל יכולה להתאים שורות בנק גם לתשלומי Outpatient.
- **הדשבורד לא כותב ל-Outpatient.**
- זה שלב 5, ומותנה בהחלטה בסעיף 3.
