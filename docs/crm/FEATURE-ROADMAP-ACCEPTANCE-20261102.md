## 1. Scope and decision rules
`P0` blocks correctness, privacy, safety, or usable source integrity; `P1` necessary daily staff workflow; `P2` optimization or new feature. Priority is not implementation authorization. Every item has **one execution owner**; do not create parallel issues, app code stores, or PR branches where work already exists. As of this audit, actual authenticated UI flows and restore drills are NOT established. No program may be called complete by counting green synthetic tests.

**Statuses:** `IN PROGRESS DRAFT`, `REUSE / IMPROVE`, `ANALYSIS`, `PROPOSED FOR APPROVAL`, `BLOCKED`. A feature marked `PROPOSED` is not a final decision. A "minor" looking stage field/finance change can affect many downstream consumers.

## 3. Technical acceptance invariant per write
Each test row **must** capture:
`role | screen/selector | sourceId | actionPayload abstract shape | API result | authoritative row/value before+after | reload | second user view | downstream acknowledgment | duplicate/retry | status | owner`.
Tests run first on dummy/staging. Store **no names, phone numbers, clinical details or real payment rows** in issues or artifacts. Do not treat mock `ok:true` alone as save acceptance. Default to fail closed on missing actor or source. Actual live writes require separate sandbox authorization and Sandra's release approval.

### Required test set, grouped by role
1. **Vered:** create lead → first contact → follow-up scheduled → visit → manager report → family decision → payment handoff → admission; cancel/no-show and stale page paths; real contact log with next task.
2. **Dana:** same authorized operational flow, every money endpoint/embedded payload/export refused or projected with no finance fields; house scope as approved.
3. **Ortal:** report awaiting verify, partial, flagged, confirmed, invoice requested; no lead notes/clinical/meeting data or unauthorised approvals.
4. **Manager:** own-house visits, report submission/no-show, expected discharge and conflict; unrelated-house access rejected server-side.
5. **Sandra/Ron:** management-read parity on modules, including revenue totals; edit/approval controls independently authorized.
6. **Two-session race:** one user changes owner/date while other has stale form; no silent lost update, confirmed outcome or explicit conflict.
7. **Network faults:** timeout before/after actual write, malformed JSON, auth expired, retry, duplicate key, reload. No 'all clear' on missing source.
8. **Released account:** prior balance remains visible; future cycle beyond stay excluded by policy; billing-anchor-on-exit handled explicitly and explained with source period.
9. **Cross-app continuation:** send accepted by Dashboard ≠ accepted/started at Outpatient; retries with stable IDs; missing return feed stays pending.

## 4. Pilot plan after release gates
**No live pilot is authorized by this document.** First complete synthetic/staging technical acceptance, source-backed data reconciliation, security/restore proof. Then propose a controlled observational pilot with Vered, Dana and Ortal plus 2 house managers; no patient write in test. For each observed workflow measure: time to complete, click count, error/retry, owner clarity, correct persisted row and re-login; collect 5 concrete confusing terms/buttons and revise the UI with a small PR. Compare classic vs new, on same role/date/filter, before retiring classic. Define rollback and backups; require Sandra's explicit go-ahead for merge and production activation.
